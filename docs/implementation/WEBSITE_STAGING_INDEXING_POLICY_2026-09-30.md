# Website Staging and Indexing Policy

Date: 2026-09-30  
Status: release-operations authority for the web beta.

## Current staging option

Observed Netlify project:

- project: `toadal-v13-site-preview`
- site id: `7c0d4199-59d8-4461-9fd9-fb3d07dc1fb4`
- visitor access: SSO team login required for all project access
- forms: not enabled

This makes it an appropriate **private review surface** while the website remains pre-release.

## Policy

### Private staging

For access-controlled staging:

- host-level access control is the primary protection;
- `noindex,nofollow` is still desirable where practical, but absence of a meta tag is not by itself a publication leak when the site is actually access-controlled;
- do not weaken access controls merely to make review easier.

### Public/crawler-accessible staging

Before any staging URL is accessible without authentication:

- every ordinary HTML route must receive `noindex,nofollow`, OR
- the host must emit an equivalent `X-Robots-Tag: noindex, nofollow` response header.

Standalone cartridge HTML must be covered too.

Do not mutate source-authority/donor files merely to inject robots metadata when a host/header solution can cover the staging surface.

### Production

Production release must deliberately remove staging-only indexing suppression.

Do not accidentally ship a production site that remains `noindex`.

## GitHub Pages

Treat GitHub Pages as a deployment surface, not as an automatic staging authority.

A push to `main` currently has deployment consequences. Therefore:

- do not use `main` merely to preview a candidate;
- do not merge planning/evidence branches to make them visible;
- prefer private Netlify review or a deliberately isolated preview mechanism;
- production/main deployment requires owner acceptance.

## Release checks

Before public beta:

1. verify exact source SHA/tree;
2. verify exact static export hash;
3. verify intended access-control/indexing state;
4. fetch representative HTML from the deployed surface;
5. verify robots/meta/header behavior;
6. verify standalone game/player routes receive the intended policy;
7. verify no staging password/SSO requirement accidentally remains on production;
8. verify production is indexable only after owner approval.

## Failure modes to avoid

- public staging with no indexing guard;
- production left noindex;
- byte-preserved donor modified just to add staging metadata;
- preview generated by merging to main;
- staging access control removed without replacing indexing policy;
- assuming a robots.txt alone guarantees non-indexing of already-known URLs.
