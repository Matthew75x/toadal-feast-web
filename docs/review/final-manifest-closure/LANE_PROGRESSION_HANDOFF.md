# Lane D — Feast Pass / Progression Handoff\n\nDate: 2026-10-02\nScope: Feast Pass, Quests, Rewards, Profile, Home Treat migration, and the website-local score API.\n\n## Persistence boundary\n\nThe lane keeps the existing four browser keys:\n\n- `toadal:web:v1:feast-pass`\n- `toadal:web:v1:quests`\n- `toadal:web:v1:discoveries`\n- `toadal:web:v1:profile`\n\nNo score key or other website namespace was added. Local scores live under `localScores` in the existing profile record. The profile keeps each game's best score and at most 50 sanitized completed runs. The schema contract now describes the bounded score record.\n\nAll player surfaces should use the runtime API. They should not read or write `localStorage` directly.\n\n## Browser API for Leaderboards and Profile\n\nAfter `guest-progression.js` loads, it boots one store and exposes it as:\n\n```js\nwindow.ToadalGuestProgressionStore\n```\n\nThe runtime module also offers `ToadalGuestProgression.getStore(window)`. Reuse this shared store; do not create a Leaderboards-specific store.\n\nRead the store through:\n\n```js\nconst store = window.ToadalGuestProgressionStore;\nconst snapshot = store.getSnapshot();\nconst scores = store.getLocalScores('wicked-bites');\nconst best = store.getLocalBest('wicked-bites');\n```\n\n`getLocalScores(gameId)` returns `{ gameId, best, runs }`. `runs` is sorted by score descending, then completion time descending. `best` is the personal best or `null`; there are no generated opponents or global ranks.\n\nRecord a completed local run through:\n\n```js\nconst result = store.recordLocalScore({\n  gameId: 'wicked-bites',\n  score: payload.score,\n  completionId: activeRunId,\n  mode: payload.mode,\n  ruleset: payload.ruleset,\n  characterId: payload.characterId\n});\n```\n\n`gameId` and `completionId` are required. `completionId` must be a bounded alphanumeric run token unique to that game run. The API accepts a finite non-negative safe integer or a trimmed string containing only decimal digits. It rejects fractions, negatives, unsafe integers, payload text, invalid identifiers, and unsupported metadata. Omitted metadata is stored as `null`; completion time is assigned by the website. Unknown payload properties are discarded.\n\nPossible failures include `invalid-game-id`, `invalid-score`, `invalid-completion-id`, `invalid-score-metadata`, `duplicate-completion`, `future-schema-read-only`, and `storage-unavailable`. Only a successful persisted score can advance the configured Wicked Bites completion quest. Recording a score does not grant XP, Sparks, Treats, badges, or entitlements by itself.\n\n## Required player-host integration\n\nThe current player host already validates message source, protocol, message type, and game ID. The Integrator owns connecting that validated event to this API:\n\n1. Load definitions and `guest-progression.js` on `/player/wicked-bites/` before using the store. The shared advanced-code progression loader currently needs the Leaderboards and player routes added to its eligibility list.\n2. Use `game:score` for the live HUD only. Do not persist it as a completed run.\n3. On a real `game:started` transition, or an explicit retry that starts a new run, create a new `activeRunId` and clear the one-completion guard. Keep the same ID if the host receives another completion notification for that run.\n4. After the validated `game:complete` message, call `recordLocalScore` once with the raw score value and that run ID. Set the guard after success or `duplicate-completion`. If storage fails, report that the local score could not be saved.\n5. Pass only metadata actually supplied by the cartridge and accepted by the host. For Wicked Bites fields not supplied, omit them so the API stores `null`.\n\nThe API requires a per-run ID so duplicate completion messages can be rejected without dropping two legitimate runs that happen to have the same score. The host remains responsible for defining run boundaries and validating the message source; local browser storage does not establish server authority.\n\nLeaderboards should read `getLocalScores('wicked-bites')` and `getLocalBest('wicked-bites')` from this shared store. Its route registration and loader eligibility remain Integrator-owned.\n\n## Required Home candy/Treat hook\n\nHome's existing interaction runtime already calls:\n\n```js\nstore.collectHomeCandy(interactionId)\n```\n\nThat method now validates the interaction and Golden Block state, writes the Home discovery and its mapped Treat collectible together through the existing rollback-based `saveMany()` path, recalculates the local Treat count, and returns `ok: true` only after both writes succeed. The current `toadal:candy-found` event remains a notification after success; do not grant a Treat from that event. Golden Block hits remain discovery-only; its candy only grants a Treat after the fourth hit reveals it and the candy is collected separately.\n\nExisting users may already have one or more Home candies in `discoveries.homeInteraction.candies`. The public migration API is:\n\n```js\nconst result = store.reconcileHomeTreats();\n```\n\nProgression page boot calls this explicit, idempotent reconciliation before rendering. It adds only missing mapped collectibles for valid saved candy IDs, recalculates Treats, and processes the matching Treat quest event. It never writes from `getSnapshot()`. Corrupt Home state or a future/read-only Pass or Discoveries record is left untouched. New candy collection is rejected if either required record cannot be safely written.\n\nTreat mapping:\n\n| Home interaction | Local Treat | Existing asset |\n| --- | --- | --- |\n| `portal-candy` | `treat-home-blue` | `asset.home.interaction.candy-blue` |\n| `lower-page-candy` | `treat-home-green` | `asset.home.interaction.candy-green` |\n| `golden-block-candy` | `treat-home-purple` | `asset.home.interaction.candy-purple` |\n\nThese are browser-local collection markers only. They are not paid currency, mobile items, or transferable rewards.\n\n## Page and route integration\n\nThe owned Feast Pass, Quests, Rewards, and Profile pages now link to `/leaderboards/`. The Integrator should register that route and allow the shared progression loader on both `/leaderboards/` and `/player/wicked-bites/`; this lane intentionally did not edit the shared page index, navigation, advanced-code, CSS, registries, or generated output.\n\nQuest events are limited to configured World and Stories visits, successful Treat collections, and valid persisted browser-game completions. Daily check-in keeps the existing UTC-day period. Weekly quests remain an explicit empty state. Local reward markers derive only from those actions, configured level milestones, and the real page discoveries; none is an account or app entitlement.\n\n## Validation\n\n`node scripts/guest-progression.test.mjs` runs the full progression suite in this environment.
