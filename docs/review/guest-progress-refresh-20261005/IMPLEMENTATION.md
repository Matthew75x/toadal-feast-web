# Keep open guest-progress views current

## Implemented behavior

An already-open Profile page previously retained stale progress after another tab saved a quest reward. The defect was reproduced through the actual exported World and Quests pages: the claim saved 10 XP in one tab while the open Profile in the other still showed 0 XP.

The existing guest store now exposes `refreshFromStorage()`, a read-only rehydration of its same four website-local records. Open progression views react to relevant localStorage change events, focus/visibility return and a persisted `pageshow`. They reread current storage; they do not trust an event's potentially delayed `newValue`, replay route discoveries, perform migration writes, grant rewards or recreate records after reset. Other games' keys, sessionStorage and unbound storage events are ignored.

Successful changes refresh XP, quest/reward state, discoveries, the selected title and the displayed local personal best through the existing renderer. A no-op focus leaves list nodes and operation messages alone. Repeated boot does not duplicate listeners or writes. Page-only memory mode remains explicitly nonpersistent.

A failed read or unsupported record keeps the last-readable value and shows an explicit refresh warning, not invented empty progress. Stored future/corrupt bytes retain their protections and are not overwritten. A later successful read recovers the display. Reset and refresh operation receipts are non-persisted metadata; newer observed state invalidates an obsolete reset result.

## Scope and limits

This is same-origin browser-local presentation refresh, not account synchronization, a new save authority, a cross-tab locking mechanism or a multi-key atomic transaction. Concurrent writers and loss of browser data remain outside this repair. Lifecycle handlers are covered; actual browser back/forward-cache admission and physical mobile execution are not certified by the controlled lifecycle event test. An always-visible tab is not promised a continuous midnight timer.

No new storage key, progression schema, XP/reward rule, game payload, companion/fullscreen behavior, account provider or telemetry activation is introduced. The single Home resource pin is updated for the changed runtime. `dist` is regenerated by the existing pinned Studio export, never edited as a replacement source.

The branch starts from merged reset repair `02569d8f177e0e82ca232e4121a6802c5e0eed95` and carries forward the independently merged Support/News increment `4d9a7259ea799385984f2b12b8b540287e9c0bc8`. That increment's authored and exported files must remain unchanged by this repair.

## Verification

- The stale 0-versus-saved-10 XP failure was reproduced before repair in both the focused test and the actual exported two-tab journey.
- Fourteen new refresh regressions plus the 44 existing progression/reset/resource-pin cases pass. Repeated runs are the same cases, not additional coverage counts.
- Two multistep Chromium journeys pass at desktop and phone-sized viewports. Each uses an actual World visit and quest button, an already-open Profile, and an actual reset button in another tab. The receiving tab makes zero additional progression writes. Exact loaded runtime hashes are verified; no unexpected page exceptions occurred.
- Local-score adapter input, read-denial/future-schema cases, suppression of storage events and the persisted-pageshow event are controlled fixtures. No game was launched. Phone width/touch settings are desktop emulation, not Android/iOS acceptance.
- Existing Studio validation/export, authored-source preservation, render freshness, route/base-path/link/staging-robots checks and the three protected game artifacts remain required.

Fast regression command:

```text
node --test scripts/guest-progression.test.mjs scripts/guest-reset-recovery.test.mjs scripts/guest-progress-refresh.test.mjs
```

Bounded browser journey, using an installed `playwright-core` module and Chrome/Chromium:

```text
node scripts/guest-progress-refresh-browser.mjs <REPORT_DIRECTORY>
```

Optional `PLAYWRIGHT_MODULE` and `CHROME_PATH` select existing tooling. The script starts only its own temporary contexts and loopback server, blocks external requests, and closes them afterward. `--baseline` is a diagnostic mode for the preserved old export, not a PASS expectation for the repaired export.

The existing Pages workflow runs the focused regressions before upload. The PR/merge/deployment receipt records delivery; this document does not infer publication from test success. GitHub Pages staging is the only delivery target for this change, not production.
